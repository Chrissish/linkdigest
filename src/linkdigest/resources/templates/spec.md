> 报告产出契约——单一事实源。
> handoff 作业单（templates/brief.md）和管线理解提示词（understand/prompts.py）
> 都从这里渲染。修改体例规则只改这个文件，两边自动一致。

分三层，别混着看：机器靠「必填」渲染和定位，「不可违反」是可回查的前提，
「可选」里没有配额——写不出来就不写。

### 3.1 必填

```json
{{required_schema}}
```

- `intent`：可以留空。但如果用户提过具体目的（「我想知道该不该照着练」、
  「这套方法能不能用到我们团队」），写进来——它会写进报告元信息，也是你做取舍的依据。
- `tags`：3-5 个内容标签词，名词或短语（「恢复训练」「马拉松」「成本估算」）。
  最多 5 个，宁缺毋滥；写内容真正讲到的东西，不写平台名这类元信息。
- `sections`：`start`/`end` 是回查锚点，渲染成一行一条的索引。
  `title` 一句话说清这段讲什么；细节不要写在这里，写进 `body`（见 3.6）。
  时间范围要和内容对得上，但不必把内容切成等长的块：天然是一整段的，就写一个。{{sections_hint}}
- `body`：这份报告的主体，写源内容的**平直整理**，不是内容评析。
  按内容自身的结构走：它讲了什么、按什么顺序推进、给出哪些具体做法、数字、判断、案例。
  只陈述源内容说了什么。不排名、不打分、不判优劣，不写「最硬 / 最弱 / 站不住 / 骗人 / 可惜 / 失败案例」这类评语；
  也不写「该拿走什么」「听众应该……」这种使用建议。
  证据不足、前后矛盾、没给出处的说法一律只进 `controversies` / `open_questions`，
  正文里不夹批注、不提前替它下结论。要体现内容之间的落差，用事实并置，不加形容词。
  长度由内容决定——内容够，写三四千字不算多；内容薄，写三百字也不算少。
  **这是整份产出里最值钱的部分，别省。**

### 3.2 不可违反

1. 只用正文里的信息。不补外部知识，不推测没出现的人名、数字、结论。
2. 报告语言一律简体中文。原话（`quotes`）保留原文，必要时在 `note` 里给中文意思。
   正文里不夹未翻译的外文词——外文术语首次出现写「中文（原词）」，之后一律用中文；
   `deal breaker` 这类口语说法写成中文意思（「一票否决的缺点」），不要原样留在句子里。
3. 转写是机器识别的，人名、机构名、专名可能有错。拿不准拼写时写职位或身份
   （「苹果 CEO」「这位记者」），不要照抄一个读起来可疑的名字，更不要另编一个；
   只有确定无误的专名才写进正文。转写给出的头衔也不许照抄放大：听到「CEO 某某」
   但与公开常识冲突时（例如对方其实是硬件负责人），只写「苹果高管」这类身份，
   不要把错误头衔连同名字一起写实。
4. {{timecode_rule}}
5. 出现互相矛盾的说法写进 `controversies`，不要替它下结论；
   材料没回答但重要的问题写进 `open_questions`。
   正文里写了「有争议」「未证实」「缺乏研究」「说法不一」的，`controversies` 里
   必须有对应条目——写在正文里却没进这一层，等于把争议埋了；全篇一条都没有，
   先回头通读正文再确认是不是真的没有。

这五条不是风格建议，是这条件内容可被回查的前提。破了，报告就没法核对。

### 3.3 可选：按内容判断，不要凑

| 字段 | 装什么 |
| --- | --- |
| `tldr` | 核心结论，条数随内容，每条一句话 |
| `data_points` | [{"label", "value", "start"}] 只放结论性数字：阈值、剂量、期限、判定标准。不参与页面渲染，只作数据层 |
| `quotes` | [{"text", "start", "note"}] 值得原样保留的话，text 保持原语言 |
| `controversies` | 材料里互相矛盾或未证实的说法 |
| `open_questions` | 材料没回答但重要的问题 |
| `terms` | {"原文术语": "中文解释"} |
| `appendix` | 通用字段装不下的东西：代码、公式、动作清单、人物表。写成 Markdown 文本（`###` 小标题 + 列表），不要输出 JSON 对象或数组；不要放时间线或章节表（`sections` 已有），不要复述数据点 |

省略的判断对象是「正文里有没有对应素材」，不是「可填可不填」：
正文里出现过的结论性数字就进 `data_points`，值得原样保留的话就进 `quotes`，
首次出现的外文术语就进 `terms`，内容的主要结论就进 `tldr`——
这四样里任何一样，只要正文有素材就不许空。只有正文确实没有对应素材时才省略。

遇到什么形状装不下，放 `appendix`，别硬塞进 `sections`。

一条 90 秒的短视频不需要 5 条 `tldr`；
一段 3 小时的播客也不该被压成 3 条。条数跟着内容走，不跟着模板走。

重点摘要只有一个模块，就是 `tldr`。不要另起一份「关键信息」——两份短句摘要必然重复，
要么合并进 `tldr`，要么写进正文。

### 3.4 去重：同一个事实只写一遍

报告只有一份读者，重复陈述等于浪费他的时间。以下几处最容易撞车：

- `sections` 自带时间码，**不要**在 `appendix` 里再画一张时间线、时间结构表、章节表。
- `data_points` 只收**结论性**数字：阈值、剂量、期限、判定标准、可复用的比例。
  正文里顺带出现的描述性数字（身高体重、场次、当日跑量、优惠码、观看数）不进表，
  写进 `body` 就够。
- `data_points` 只作数据层（下游程序取用），页面不渲染；数值该讲的地方照讲在 `body` 里，
  不必因为「表里已经写了」而在正文省掉，也不用为了填表把正文里的数字再抄一遍。
- `tldr` 写内容的主要结论，`body` 写内容怎么展开，`sections` 写定位。三者不互相复述措辞。
- `appendix` 只装通用字段真的装不下的东西：代码、公式、动作清单、人物表。
  它不能是前文任何一节的重排版本。

拿不准的时候删掉，不要留着凑完整。空字段渲染时不会出现，少写不会有洞。

输出前自检一遍：把 `body` 通读，问每个可选字段「正文里真的完全没有素材吗」——
有素材而留空，是漏，不是简；删掉的判断只适用于「写了会和别处重复 / 拿不准真伪」的内容。

### 3.5 正文口径：整理，不是评论

`body` 是给没看过原件的人看的内容整理，不是影评，也不是内容质量诊断。
读者要的是「这条内容讲了什么」，不是「你怎么看这条内容」。判断性的东西已经有地方放：
`controversies` 放矛盾与未证实，`open_questions` 放材料没回答的。

| 不要写 | 改成 |
| --- | --- |
| 这是全片最硬的一段 | 直接写这一段给了什么：判据、数值、动作 |
| 论证站不住，只有个人经历 | 依据是他自己的经历和一次假想场景 |
| 这段只有口号，没有剂量 | 这一段给了方向，没有给动作、频率或周期 |
| 可惜这个论点被八卦拖累了 | 他在同一段引用了第三方的私人生活细节 |
| 最有说服力也最不严谨 | 他给出的三条原因分别是…… |
| 听众应该按这个权重分配注意力 | （删掉，正文不给使用建议） |

允许写的是结构性描述：内容分几段、时间码怎么对应、哪一条是转折、哪一处没有展开。
这些是「它在讲什么」，不是「它讲得好不好」。两者的分界是：删掉形容词之后，
句子还能不能从原文核对出来。核不出来的，就是你的判断，不该出现在正文里。

### 3.6 `body` 与 `sections` 的分工：正文给人读，分段给人查

- `body` 是页面上的正文，也是唯一叙事线：按内容顺序讲清它说了什么，细节、数字、动作、案例都放这。
- `sections[].points` 是给下游程序用的逐段要点（每段 2–4 条），**不参与页面渲染**：
  页面只取 `title` 和时间码做索引。所以不要为了「跟正文不重复」把它清空——
  它是数据的粒度层，正文是阅读层，两者重复不会让读者读两遍。
- `title` 一句话说清这段讲什么。索引里只有标题，写含糊索引就废了。
- 结构化强的内容（编号清单、按周时间线、分步教程）正文照原顺序讲即可，
  不必绕开分段结构——页面上它不会再被复述一遍。

读者顺序是 速览 → 分段索引 → 正文：速览给结论，索引给骨架（先看到全片怎么分段，再顺着读），
正文给内容。所以索引的 `title` 要能单独看懂，否则读者看完索引仍不知道这份材料讲了什么。
